# Results of 2026-11-09: hashing a node in one call, and the allocator

Where the server's time goes while it takes SETs, and what two changes to
it are worth. The same virtual machine as
[`../2026-11-09-linux-vm/`](../2026-11-09-linux-vm/). These numbers compare
versions of Umbrachyx on one machine; they are not in the README's table,
which is taken on fixed machines.

## Machine

- A Linux virtual machine on an Apple M4 MacBook Air (32 GB), macOS
  26.6.2: Colima with the macOS Virtualization framework, 2 virtual CPUs,
  4 GiB of memory, Linux 6.8 (aarch64). Everything ran in a Debian 12
  container inside it, the client on the same two CPUs as the server.
- Rust 1.98.0 (the version the repository pins), built with `--release`.
- The client is `valkey-benchmark` from Valkey 9.1.3. Profiles are from
  `perf record` without call graphs, kernel symbols unresolved.
- Synthetic data only: random keys and 32-byte values generated by
  `valkey-benchmark`.

## The binaries

| Name | Code |
|---|---|
| `system` | `20c5df9`, the system allocator (glibc's) |
| `jemalloc`, `mimalloc` | `20c5df9` with that allocator as the binary's global allocator |
| `buffer` | the commit that adds this folder: a node's fields gathered into one buffer and hashed with one call |
| `buffer-jemalloc` | `buffer` with jemalloc, as the commit after it builds by default |

## Files

| Folder or file | What | Command |
|---|---|---|
| `allocator-only/run-1..3/` | `system`, `jemalloc`, `mimalloc` | `alloc.sh <name> <binary>` for each binary in turn, three rounds |
| `node-hash/run-1..3/` | `system`, `buffer`, `buffer-jemalloc` | the same |
| `profile/` | one profile each of `system`, `buffer`, `buffer-jemalloc` | `prof.sh <binary>` |

`alloc.sh` starts a fresh server and sends, from 50 clients: 200,000 SETs
pipelined 64 deep over 200,000 keys, 100,000 GETs, 50,000 SETs one at a
time, and the 200,000 pipelined SETs again. Each row is
`valkey-benchmark --csv` output with the binary and the step in front. The
last row is the resident size before and after, and the bytes it grew per
SET after the first pass. `prof.sh` records the server for 14 seconds
while it takes a second pass of pipelined SETs and then 300,000 GETs, and
prints the shares by library and the top symbols.

## What they show

- **The node hash took about 42% of the server's time** under SETs
  (`blake3::portable::compress_in_place` with its callers), more than
  walking the tree for GETs (about 14%). Fed a few bytes at a time,
  BLAKE3 compresses one 64-byte block after another without SIMD; given
  a node's bytes at once, it hashes whole 1 KiB chunks four at a time with
  NEON. Hashed in one call, the share is about 33%; nodes under 1 KiB,
  most internal nodes, still take the one-block path.
- Medians of three, SETs a second: pipelined, 50,544 before and 61,501
  after (first pass), 45,496 and 53,691 (second pass); one at a time,
  28,137 and 31,949. GETs do not hash and stay where they were. The
  ranges of the three runs do not overlap for the pipelined SETs.
- **The allocator alone is within the noise**: glibc's malloc took about
  5% of the time, and the medians of jemalloc and mimalloc differ from it
  by less than the runs of one binary differ from each other. Memory per
  SET moves by 1 to 2%: the 3.2 KB a SET keeps is data, not fragmentation.
- **With the hash in one call, jemalloc is worth more**: each hash now
  fills a buffer, and with jemalloc glibc's share falls from 12% to 6%.
  Pipelined SETs 68,190 and 63,251 a second, one at a time 35,236, about
  10 to 18% over `buffer`. The ranges do not overlap for the pipelined
  SETs; one at a time, they do.
