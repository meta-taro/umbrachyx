# ベンチマークと堅牢性試験のルール

速さと壊れにくさは、実績の代わりに数字で示す。数字は、誰でも同じ手順で流し直せる形で公開する。

## 1. いつ流すか

| いつ | どこで | 何を | 公開するか |
|---|---|---|---|
| push のたび | GitHub の CI（自動） | `bench/` の3本と、堅牢性の試験すべて | artifact に残すだけ。README には載せない |
| 速さ・耐久性に触れる変更の commit 前 | 手元 | 変更に関係する測定 | 載せるなら、同じ commit で README も直す |
| **大きい版のリリース（機能を足す。例 0.2.0・1.0.0）** | 固定の測定機（§2） | 3本 × 3回と、堅牢性の試験すべて | `bench/results/` と README の表を更新する |
| **不具合の修正版のリリース（例 0.2.1）** | CI。条件に当たるときだけ固定の測定機 | 下の条件を参照 | README の数字は変えない。測ったなら `bench/results/` には置く |

- リリースは細かく刻まず、機能をまとめて大きい版で出す。不具合の修正だけは、修正版としてすぐ出してよい。
- **どのリリースも、リリースする commit で CI の堅牢性の試験がすべて通っていること**（強制終了100回・ログの強制終了1,000回・シミュレーション1万通り、Linux と Windows）。これが障害の確認になる。
- 修正版でも、次のどちらかに当たるときは固定の測定機で1回測る。
  - ログ・書き込みの仕組み（committer）・木・サーバのどれかを触った。
  - CI のベンチマークが、前のリリースの run より3割以上遅い（CI 機はもともと3割ほどぶれるので、それを超えたときだけ）。
- 測って遅くなっていたら、原因を調べてからリリースする。
- CI 機は他と共有しているので数字がぶれる。前の run と比べて遅くなっていないかを見るためだけに使い、README の表にはしない。
- 大きい版で固定の測定機の測定を飛ばしたまま、リリースしない。

## 2. 固定の測定機（AWS と GCP の2台）

バージョン間で比べられるように、条件を毎回そろえる。大きい版では両方で測る。修正版で測るときは AWS だけでよい。

| 項目 | AWS | GCP |
|---|---|---|
| 機種 | EC2 `m6id.xlarge`（4 vCPU・16 GiB、ローカル NVMe 237 GB 付き） | Compute Engine `n2-standard-4`（4 vCPU・16 GB）＋ ローカル SSD（NVMe）1枚 375 GB |
| リージョン | `ap-northeast-1`（東京） | `asia-northeast1`（東京） |
| OS | Ubuntu 24.04 | Ubuntu 24.04 |
| ログを置く場所 | ローカル NVMe（ネットワークディスクにしない） | ローカル SSD（ネットワークディスクにしない） |
| 支払い方法 | オンデマンド | オンデマンド |

- スポット／プリエンプティブルは途中で止められ、測り直しになるため使わない。
- **条件を変えるときは**、理由を `docs/comparison.md` に書き、新旧の両方の機械で同じ commit を1回ずつ測って、つなぎ目を残す。
- 毎回 Valkey・Dolt・PostgreSQL も同じ機械で測り直す。倍率は、同じ機械で測った値同士でしか出さない。
- ほかの機械（ノート PC、Xserver VPS など）の数字は、参考の列として README に並べてよい。そのときは機械・プラン・CPU が専有か共有か・ディスクの種類を書く。

## 3. 流すもの

新しい Ubuntu 24.04 の機械では、`bench/cloud.sh <機械名> <ローカル NVMe 上のフォルダ>` が下の全部を3回流し、結果と機械の情報を `~/umbrachyx-results/<日付>-<機械名>/` にまとめる。中身は次と同じ。

```sh
bench/umbrachyx.sh
bench/valkey.sh
bench/postgres.sh             # PostgreSQL の主キーでの読み取りと更新（Ubuntu の版）
bench/connections.sh          # 先に ulimit -n 65536
bench/memory.sh               # 同じ SET を2回流したときのメモリ（RSS）
cargo run --release -p umbrachyx --example compare -- 1000000 <dir>   # 差分と読み込み（Dolt と同じデータ）
bench/dolt.sh <dir>           # Dolt の差分と読み込み（Dolt 2.6.2 のリリース版）
cargo test -p umbrachyx --release --test server_crash -- --ignored --nocapture
cargo test -p umbrachyx --test crash -- --ignored --nocapture
cargo test -p umbrachyx --lib --release ten_thousand_seeds -- --ignored --nocapture
```

- ベンチマークは3回流す。README には中央値を書くか、幅で書く。
- 堅牢性の試験が1つでも落ちたら、リリースしない。落ちた試験を消したり、回数を減らしたりして通さない。

## 4. 公開の仕方

- 生の出力は `bench/results/<日付>-<機械>/` に置き、そのまま残す。CSV を手で直さない。
- 同じフォルダの `README.md` に次を書く：機械・OS・版（Rust、Valkey）・測った commit・流したコマンド。
- README の「Numbers so far」と `docs/comparison.md` の表は、結果を置いたのと**同じ commit で**直す。
- **負けた行も同じ表に載せる。**勝った行だけを選んで載せない。
- 測っていない数字は書かない。機械によって倍率が大きく変わるものは、両方を並べる（例：書き込み中の GET は、ノート PC で約650倍、Linux の CI 機で約20〜28倍）。

## 5. 費用と後片付け

### 費用の目安（2026-11-04 時点。使う前に公式の料金表で確かめる）

| 項目 | 目安 |
|---|---|
| `m6id.xlarge` 東京・オンデマンド | 約 $0.31/時間（バージニア北部 $0.237 に、東京の割増を掛けた見積もり） |
| `n2-standard-4` ＋ ローカル SSD 1枚、東京 | 約 $0.3/時間（AWS と同じ水準と見ている。公式の料金表で未確認） |
| 起動ディスク（gp3 30 GB）・公開 IPv4 | 1時間あたり約 $0.01 |
| 1台での1回の測定（組み立て・3回の測定・堅牢性の試験・回収で、約1.5時間） | **約 $0.5（1ドル150円で約75円）** |
| 大きい版1回（AWS と GCP の2台） | **約 $1（約150円）** |
| 大きい版が年4回、測る修正版が年8回の場合 | 年に約 $8（約1,200円） |
| GitHub の CI（public リポ） | 無料 |
| Xserver VPS（別の目的で契約するものを1回借りる） | 増える費用なし（8 GB プランは月3,201円からという記事がある） |

### 消し忘れがいちばん高い

1台を消し忘れると、**1か月で約 $230（約3.4万円）**かかる。1回の測定の約450倍。人の注意に頼らず、**VM を作るときに、3時間で自分から消える設定を必ず付ける。**

| | 作るときの設定 |
|---|---|
| AWS | 「シャットダウン動作：終了（Terminate）」にする。ユーザーデータに `#!/bin/bash` と `shutdown -h +180` を入れる |
| GCP | 実行時間の上限を3時間、上限に達したときの動作を「削除」にする（`--max-run-duration=3h --instance-termination-action=DELETE`） |

- これで、消し忘れたときの最悪の額は、約3時間分（約150円）になる。
- AWS の時間の上限は、`bench/cloud.sh` ではなく起動時に仕掛ける。スクリプトが途中で止まっても、流さなかった場合でも効くようにするため。
- この設定が無い VM には、AI は測定を始めない。始める前に、`sudo shutdown --show`（AWS）か、インスタンスの設定（GCP）で、上限が付いていることを確かめる。
- 測定は約1時間で終わる。結果は上限の前に回収する。
- 月額の定額で借りている VPS（Xserver VPS など）は、自分から消える設定の代わりに、測定のあとで片付ける（`~/umbrachyx-results` を回収したら、測定用のフォルダ・`~/umbrachyx`・Rust を消す）。完了の知らせには「片付けた」と書く。
- **開始と完了を、もう一人（人か別のエージェント）に知らせ、二重に確かめてもらう。**
  - 開始：どのクラウド・機種か、作った時刻、自動で消える時刻
  - 完了：結果の置き場所と、VM を終了して一覧から消えたのを確かめたこと
  - 自動で消える時刻を過ぎても完了の知らせが無い、または完了に「消した」が無いときは、知らされた側が声をかける
- 測定が終わったら、**結果を回収してから VM を「終了（terminate）」する。**「停止」だけにしない（起動ディスクの課金が残る）。
- 消したあと、EC2 と Compute Engine の一覧に実行中のものが無いことを確かめる。ローカル SSD も一緒に消えていることを確かめる。
- AWS Budgets と GCP の予算アラートで、どちらも月 $10 を超えたら通知が来るようにしておく（設定は人が行う）。

## 6. 権限と安全

- AWS のアカウント・鍵・権限の設定、SSH の鍵は、**人が作って入れる。**AI は作らない・置かない・貼らない。
- 自動にするときは、長く使える鍵を GitHub に置かずに済む方式（OIDC）を使う。
- umbrachyx も Valkey も `127.0.0.1` だけで待ち受ける。測定用のポートを外へ開けない。外から入れるのは SSH だけにする。
- データは合成データだけを使う。実在のサービスのデータは入れない。

## 7. sshboard で流す手順

測定機には、sshboard（SSH の画面を人と AI が一緒に見るツール）でつなぐ。AI が何をしたかは、すべて sshboard の画面に残る。

| 順 | 誰が | 何を |
|---|---|---|
| 1 | 人 | AWS / GCP のコンソールで VM を作る（§2 の条件）。SSH の鍵を作り、ssh-agent に入れる |
| 1b | AI | sshboard の `register_connection` で、その VM への接続を登録する（宛先・ユーザー名・ポートだけ。鍵は ssh-agent のものを使い、鍵のパスや秘密は渡さない） |
| 2 | 人 | sshboard のコンソールを開き、「AI に渡す」で AI に渡す |
| 3 | AI | ローカル NVMe をフォーマットしてマウントし（sshboard が AI の `mkfs` を拒むなら、ここは人が行う）、`git clone` で測るタグを取り出して、`bench/cloud.sh` を `nohup` で流す |
| 4 | AI | 結果のフォルダを sshboard で回収し、`bench/results/<日付>-<機械名>/` に置いて、README の表を直す（commit まで） |
| 5 | AI | コンソールを人に返す |
| 6 | 人 | VM を終了（terminate）し、一覧から消えたことを確かめる。push する |

- **VM を起動してから測定を始めるまでの待ち時間は、障害として扱う。**時間で課金され、3時間で消える機械なので、止まっている分だけ費用と測定の余裕を捨てる。2026-11-12 に、人の承認（ホストの確認と「AI に渡す」）を約30分待った。AI が承認のお願いを返事の先頭に書き、末尾を状況の表で終えたため、人は「もう進んでいる」と受け取った。
  - **起動する前に、人が sshboard の画面の前に居ることを確かめる。**起動のあとに要る操作（ホストの確認・「AI に渡す」）を、起動の前に伝えておく。
  - **人の操作を待つときは、返事の最後の行に「何を・どこで押すか」と「押すまで止まっている」を書く。**人は返事を下から読む。
  - **起動したあとは、測定が走り出すまで AI は待ちに入らない。**`await_answer` で待ち続け、2分たっても答えが無ければ、同じお願いを最後の行にもう一度書く。
  - 待った時間は、結果のフォルダの `README.md` に書く（何分・なぜ）。
- **ローカル NVMe のデバイス名を決め打ちしない。**同じ機種でも、起動のたびに `nvme0n1` と `nvme1n1` が入れ替わる（2026-11-12 の2回で逆だった）。`lsblk` で、マウントされておらず大きさが約 220 GB のディスクを選んでから `mkfs` する。
- AWS の起動画面が動かないときは、同じコンソールの CloudShell から `aws ec2 run-instances` で同じ条件を指定して起動してよい。起動のあと、シャットダウン時の動作が `terminate` であることを `describe-instance-attribute` で確かめる。
- 測定機は使い捨てで、秘密情報を置かない。それでも、渡されたコンソールで AI がやるのは手順3〜5だけにする。
- 測定機への接続の登録は、AI が `register_connection` で行ってよい（2026-11-11、オーナーの判断）。鍵・パスワード・パスフレーズは扱わない。
- `readonly.toml`・`operations.toml`（AI に何をさせてよいかの一覧）は、引き続き人が書く。AI は書かない。
- `nohup` で流すので、SSH が切れても、コンソールを人が取り返しても、測定は最後まで走る。進み具合は `nohup.out` と結果のフォルダで見る。
