| D4 | 2026-10-27 | 最初に作るのは**単一ノードの key/value コア**。SQL・同期は後 | 構想の Interface。小さいコアの方が速くしやすく、検証もしやすい |
| D5 | 2026-10-27 | **決定的シミュレーション試験の最初の対象はログ**（構想の Open question 5） | ログが真実なので、ログが壊れると木も履歴も全部壊れる。木と同期はログの上に乗る |
| D6 | 2026-10-27 | 時間モデルは**トランザクション時間のみ**。有効時間は後から足せる形にだけしておく（Open question 1） | 構想の現行案を追認。最初の用途（ゲーム運用）に有効時間の問いが無い |
| D7 | 2026-10-27 | 権限トークンは**自作しない**。biscuit を第一候補に Phase 0 で試作し、致命的な不足が出たときだけ他を見る（Open question 2） | 狭めることしかできない譲渡（attenuation）と、オフラインでの検証が最初から入っている。認可の仕組みを自作すると、それ自体の検証が要る |
| D8 | 2026-10-27 | 試験とベンチのデータは**合成データ**（ゲームの所持品・通貨の模擬）で作る。実在のサービスのデータを入れない | 結果を公開するため。公開できない入力で出した数字は、他人が検算できない |
| D9 | 2026-10-27 | 道具カードは配らない。ベースルールは OSS 版。公開範囲は毎回 `gh api` で実測する | 横断の OSS と同じ扱い |
| D10 | 2026-10-27 | **数字が出るまで README に速さを書かない**。いまの README の「Status: concept」を保つ | 構想の原則 5。測っていない速さを書くと、最初に読んだ人の信用を失う |
