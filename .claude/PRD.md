# umbrachyx PRD（叩き）

## 背景

- dbboard を作る中で、既存の DB には AI に任せるための約束事が無いと分かった。
  具体的には、出どころ・承認・戻せること・最小権限が欠けている。
  これまでは、本体（エンジン）は需要の合図が出てから作る方針だった
- 2026-10-27、メンテナの判断で**本体から作る**ことになった。dbboard の派生として、別リポ・別製品とする（D1）
- 何を作るかは `docs/concept.md` が正本。この PRD は構想を作業の単位に落とすためのもの

## 目的

メモリ速度で読み書きでき、すべての値が履歴を持つ DB を作る。
履歴には「いつ・何から何へ・誰が・なぜ・誰が承認したか」が入る。
**呼び出し側（AI エージェント）を信用しない**ことを前提に置く。

## 最初の用途

ゲーム運用（所持品・ゲーム内通貨・プレイヤーの状態）。構想の 5 つの問いに答えられることが目標。

1. 「アイテムが消えた」→ いつ、どの変更で消えたか
2. 「この口座に通貨が増えている」→ どの経路で増えたか
3. 「全員に間違った報酬を配った」→ その付与だけを戻す
4. 「新イベントを実データで試す」→ 枝の上で試し、本番に触れない
5. 「アカウントを消して」→ その人のデータだけを読めなくし、ほかの履歴は残す

## 範囲（いま作るもの）

- 単一ノードの key/value コア
- 追記専用ログを真実とする書き込み（ログに書けたら確定）
- メモリ上の永続木（Merkle）。commit・枝・差分・merge（衝突は検出まで）
- 出どころ（誰が・なぜ・誰が承認したか）を commit とセルに持つ
- 権限トークン付きの MCP。エージェントの書き込みは必ず枝に入る
- dbboard から履歴を見るアダプタ（行の履歴・セル差分・最終変更者）
- 暗号消去（主体ごとの鍵を壊して消す）と、列ごとの保持方針

## やらないこと（いまは）

- SQL 層（key/value コアが固まってから載せる）
- 複数ノードの同期・CRDT・anti-entropy（構想の「Sync and scale」はフェーズ 4 以降）
- 何にでも最速であること・Postgres と幅で競うこと・キャッシュとして使うこと（構想の Non-goals）
- 「AI が書いたから安全」と言うこと。安全の主張は試験の結果で示す

## 成功の測り方

構想の「How "better" will be measured」に従う。**数字が出るまで README に速さを書かない**（D10）。

| 比べる相手 | 測るもの | 初めて測るフェーズ |
|---|---|---|
| Redis / Valkey | 読み書きの p99 遅延 | 1 |
| Dolt | 履歴・差分・merge の速さ | 1 |
| Postgres＋監査トリガ | 同じ履歴を持つための手間と書き込みコスト | 2 |
| すべて | 乗っ取られたエージェントが壊せる範囲・漏らせる範囲 | 2 |

## 非機能要件（OSS）

- public リポ。README・docs・commit メッセージは英語
- commit author は GitHub の noreply に固定する（当該リポだけ）
- 組織内の呼び名・個人名・ほかの案件名を、公開物（ファイル・Issue・ラベル・リリースノート・ワークフロー名）に入れない
- 試験の結果を公開する（構想の原則 5「信用は年数でなく証拠から」）

## リスク

| リスク | 手当て |
|---|---|
| dbboard と同じ開発エージェントが兼務するので、dbboard の版出しが止まる | dbboard の利用者向けの修正を先に出す。umbrachyx は出す日を約束しない（構想段階の OSS） |
| 「確定した書き込みがクラッシュで消える」を見落とす | Phase 0 の最初に耐久性を測る。決定的シミュレーション試験の最初の対象はログ（D5） |
| 権限を設定任せにして、結局広くなる | 権限トークンを自作しない。biscuit で試作し、狭めることしかできない形を試験で確かめる（D7） |
| 構想が大きく、最初の 1 本が出ない | フェーズごとに「動くもの」を出す。Phase 1 の終わりに、ゲーム運用の問い 1〜4 を合成データで実演する |
