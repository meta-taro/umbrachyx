# umbrachyx ロードマップ（叩き）

各フェーズは「動くもの」で終わる。完了条件は、コマンドの結果で判定できる形にしてある。

## Phase 0 — 実測で決める（設計の前提を潰す）

| # | 中身 | 完了条件 |
|---|---|---|
| 000 | リポの初期整備 | CI（fmt・clippy・test）が既定ブランチで緑。commit author が noreply |
| 001 | 追記ログの耐久性 | プロセスを強制終了する試験を 1,000 回回し、確定を返した書き込みが 1 件も消えない（Windows と macOS の両方） |
| 002 | 木の方式を選ぶ | 差分のコストが「データの量」でなく「変更の量」に比例することを、ベンチの表で示す。選んだ方式と理由を decisions に書く |
| 003 | 権限トークンの試作 | 範囲（行・列・期限・目的）を絞ったトークンで、範囲外の読み書きが失敗する試験が通る。譲渡のときに広げられないことも試験で確かめる |
| 004 | 決定的シミュレーション試験の土台 | 同じ seed で 2 回回すと同じ結果になる。故障を注入したログの復元試験がこの土台の上で回る |

## Phase 1 — 単一ノードのコア

- key/value の読み書き（メモリ上の木から返す）
- ログに書けたら確定とし、ログから木を作り直す
- commit・枝・差分・merge（衝突は検出まで）
- 出どころ（誰が・なぜ・誰が承認したか）を commit に、最終変更者をセルに持つ
- 保持方針はまだ「全部残す」だけ

**完了条件**:
- 合成データで、PRD の問い 1〜4 をコマンドで実演できる（実演の手順を `docs/` に英語で置く）
- Redis / Valkey との p99 と、Dolt との差分の速さを、同じ合成データで測った表がある。速さを README に書いてよいのはここから

## Phase 2 — MCP と dbboard

- 権限トークン付きの MCP。エージェントの書き込みは必ず枝に入る。道具を足しても、乗っ取られたエージェントが届く範囲は広がらない
- dbboard のアダプタ（行の履歴・セル差分・最終変更者）

**完了条件**:
- dbboard の画面で、umbrachyx の行の履歴とセル差分が見える（キャプチャで確かめる）
- 「乗っ取られたエージェント」の試験（範囲外を読む・枝を飛ばして本番へ書く・トークンを広げる）がすべて失敗することを確かめ、その結果を公開する

## Phase 3 — 消すべきものを消す・保持方針

- 主体ごとの鍵による暗号消去
- 列ごとの保持方針（全部残す・区間ごとに 1 件へ圧縮・履歴なし）

**完了条件**:
- 鍵を壊した主体の値は読めないが、履歴の形（何がいつ変わったか）は残る、という試験が通る（PRD の問い 5）

## Phase 4 以降 — いまは作らない

SQL 層、複数ノードの同期、CRDT、anti-entropy。Phase 3 が終わってから並べ直す。
